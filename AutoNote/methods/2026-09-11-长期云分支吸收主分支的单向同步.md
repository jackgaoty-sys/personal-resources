## 结论

当 Cloud 与客户端共用代码但发布边界不同时，应使用“主分支定期单向进入 Cloud 长期分支”的策略，禁止 Cloud 反向合并到主分支。

## 适用场景

- 两个产品形态共用核心、协议和前端，但部署能力与安全边界不同。
- Cloud 需要租户化适配，而主分支仍服务桌面端或移动端。

## 方法

1. 从确定的 Cloud 基线创建独立长期分支。
2. 同步前核对远端主分支真实 HEAD、fetch refspec 和本地远端跟踪引用，记录确切 commit。
3. 在临时分支或 worktree 中先模拟合并，把差异分成“以主分支为基础”“保留 Cloud 边界”和“需要语义重组”三类。
4. 正式合并时使用主分支的通用修复和协议，再重新叠加 Cloud 的租户隔离、Sandbox、能力开关和发布边界；避免对冲突文件整体选择 `ours` 或 `theirs`。
5. 将 Cloud 适配保持在运行模式、路由装配、存储和发布入口，尽量不复制共享业务代码。
6. 每批同步都执行 Cloud 隔离回归、客户端共享契约回归，并在原始主分支快照复现非预期失败以判断是否由合并引入。
7. Cloud 镜像、二进制和发布目录使用独立命名，不覆盖客户端产物。

## 边界与反例

- 不应通过“发布时再小心”代替源码和产物的隔离。
- 若两个产品已无法维持稳定共享契约，应考虑拆分独立程序入口甚至仓库，而不是无限扩大条件分支。
