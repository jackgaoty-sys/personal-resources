## 结论

多租户 Plugin 功能必须让安装、查询、更新、启停、卸载和对话运行时全部使用同一租户事实源；只隔离查询接口会造成“安装后消失”或“显示安装但不生效”。

## 适用场景

- 从单用户桌面 Plugin 系统改造为多租户 Cloud 服务。
- Plugin 中包含可被 Agent 加载的 Skill 或 MCP 组件。

## 方法

1. 从经验证的 Web Session 派生租户 ID，再派生独立的 Lifecycle、Installer、ledger 和包目录。
2. 所有写操作和状态查询都通过同一租户上下文，不得一部分访问进程全局账本。
3. 每次对话从该租户 ledger 计算已启用组件，并注册到请求级 Skill Loader 和 Sandbox mount。
4. Capability 选择也使用请求级租户 Catalog，不得使用 Agent 进程全局 Catalog。
5. 运行时名使用 `plugin-id + component-id`类似的隔离命名，防止不同 Plugin 包含同名目录时冲突。
6. 重启后从持久 ledger 重建运行时，不依赖短期内存状态。

## 为什么有效

在已验证案例中，安装写全局账本、刷新读租户账本，导致安装结果短暂出现后消失；全局账本中其他 Plugin 也被误作当前安装结果返回。将全链路收敛到租户事实源后，刷新、运行和跨租户隔离同时恢复。

## 边界与反例

- 仅把 HTTP handler 改为租户 ledger 不够；如果 runtime adapter 仍为空实现，Plugin 仍然不能被 Agent 调用。
- Skill 已接入 Sandbox 不代表 MCP 也已接入；不同组件类型必须分别验收，未实现时保持 fail-closed。

## 验证记录

- 2026-09-11：完整 HTTP 安装、刷新、双租户 installed 状态、Skill Loader 和 Sandbox mount 自动化通过。
