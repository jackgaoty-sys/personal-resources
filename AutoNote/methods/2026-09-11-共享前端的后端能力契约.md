## 结论

同一前端服务多种运行形态时，应由后端统一返回细粒度能力契约，前端据此显示、禁用或隐藏功能，而不在每个页面散布运行模式判断。

## 适用场景

- Web、Desktop、Mobile 或私有化部署共用一套 UI。
- Cloud adapter 需要逐项完成，能力上线节奏不一致。

## 方法

1. 提供登录前可读的能力端点，返回运行模式和独立功能开关。
2. 按业务能力拆分，不用一个笼统的 `isCloud` 替代，例如文献库、定时任务、Plugin Lifecycle、MCP 分别表达。
3. 导航、直接 URL 路由、页面预取和操作按钮全部使用同一契约。
4. 新 adapter 完成租户隔离和失败关闭测试后，只需开启对应能力。
5. 开发全开必须使用独立显式环境开关，不进入生产配置。

## 为什么有效

能力契约把“UI 是否可达”与“后端 adapter 是否完成”变成可测的单一事实源，减少页面间行为不一致和后续重复修改。

## 边界与反例

- 能力开关不是权限校验；后端仍必须校验身份、资源归属和路由边界。
- “显示功能”不等于 adapter 已能安全运行，开发全开不能作为上线验收证据。

## 验证记录

- 2026-09-11：统一 Runtime Capabilities 接入导航、路由和 Plugin 操作，各 Cloud adapter 可逐项开启。
