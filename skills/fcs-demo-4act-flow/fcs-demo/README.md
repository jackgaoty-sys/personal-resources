# 飞控系统演示 · FCS Demo

在**网页**里运行的有人机飞控系统演示。飞控不是界面装饰——它夹在"侧杆"和"舵面"之间形成真闭环，切换法则或注入故障会**真实改变飞行结果**。

---

## 快速开始

```bash
cd fcs-demo
npm install          # 首次
npm run dev          # 开发服务器 → http://localhost:5173
```

浏览器打开后会自动加载 JSBSim WASM、把飞机配平到 3000ft / 110kt 平飞，然后就能操纵。

**操作**：`W/S` 推杆/拉杆 · `A/D` 滚转 · `Q/E` 偏航 · `T/G` 油门 · `R` 重置

**演示**：底部控制条可切换飞控法则、注入故障。

---

## 架构

```
浏览器
├─ 显示层 src/displays/cockpit.js    PFD / ECAM（Canvas 2D）
├─ 视景层 src/scene/scene3d.js        3D 外部视景（Three.js / WebGL）
├─ 交互层 src/main.js                定步长循环 + 键盘 + 演示控制条
├─ 飞控层 src/fcs/fcs.js   ★核心    控制律 / 包线保护 / 模式降级 / 故障注入
└─ 适配层 src/fdm/adapter.browser.js  封装 JSBSim WASM（真 6-DoF 动力学）
        ↕ fcs/*-cmd-norm（直通通道）
   JSBSim WASM（1.5MB）→ 气动力矩 → 飞机响应
```

**闭环怎么成立的**：JSBSim 里 c172p 的 `<flight_control>` 块是**纯直通**的（只有增益和限幅，没有增稳、没有自动驾驶）。所以每一帧：

1. 读飞行状态（姿态、角速率、迎角、过载）
2. `fcs.update()` 算出舵面指令
3. 写入 `fcs/elevator-cmd-norm` 等属性
4. JSBSim 把指令转成真实舵面偏转 → 气动力矩 → 下一帧状态改变

指令和响应在同一个积分回路里，这就是"飞控真的影响飞行"的技术含义。

## 3D 外部视景

拟真度按性价比排序实现（**不是靠堆多边形**）：

1. **正确的地平线与透视** — 相机在机体坐标系里跟随，机头朝 -Z
2. **视差** — 地面是固定不动的 90km 平面，飞机在它上面移动；树木/云循环复用
3. **光照与大气** — 方向光 + 半球光、天空穹顶着色器、雾遮住地面边缘
4. **细节** — 跑道、螺旋桨转速跟随油门

**坐标约定**：1 单位 = 1 米，Y 向上，+X 东，+Z 南（北 = -Z）。飞机欧拉序 `'YXZ'`：
`rotation.set(pitch, -yaw, -roll)`（符号是推导出来的，改之前先验证）。

**四种相机**（按钮或 `C` 键切换）：追机 / 座舱 / 塔台 / 环绕。

**想换更好看的飞机**：`scene3d.js` 的 `buildAircraft()` 现在是程序化建模（胶囊机身+盒子机翼），
换成 glTF 模型只要把该函数体换成 `GLTFLoader.load()`，其余代码不用动。
同理地面贴图 `makeGroundTexture()` 可以换成真实卫星影像。

**JSBSim → 3D 的定位**：用 `position/lat-geod-deg` / `position/long-gc-deg` 的增量换算成米。
注意 `position/latitude-deg` 恒为 0、`ic/lat-geod-deg` 也不等于 `reset00.xml` 里的数值，
不要用错属性（`position/distance-from-start-lat-mt` 也可用，且直接就是米）。

**性能**：高空自动隐藏树木实例；云的透明度与雾参与深度裁切。

### 视角模式（三种）

`chase` 追机 / `cockpit` 座舱 / `cinematic` 环绕。按 `C` 或底部按钮轮换。

### 键盘

| 键 | 作用 |
|---|---|
| `W`/`S`（或 `↑`/`↓`） | 俯仰（拉杆 / 推杆） |
| `A`/`D`（或 `←`/`→`） | 滚转 |
| `Q`/`E` | 偏航 |
| `T`/`G` | 油门增 / 减 |
| **`空格`** | **暂停 / 继续** |
| `R` | 重置（开始新一次运行，会解除暂停） |
| `C` | 切换视角 |

**暂停的语义**（`空格` 或顶部「暂停」按钮）：既不推进物理、也不累积时间。
所以恢复时**不会有“追赶爆发”**——不会因为暂停了 30 秒就在恢复瞬间
狂跑 30 秒的物理。实现上：暂停分支直接 `return`，`acc` 原封不动；
传给 `scene.update` 的 `dt=0`，否则螺旋桨会继续转、环绕视角会继续绕。
（`spinProp` / `setControls` 都是 `* dt` 形式，`dt=0` 安全。）

> **坑**：`keydown` 长按会连发（`e.repeat`）。不加拦截的话，按住空格会疯狂
> 切换暂停。现在统一在分发离散动作前 `if (e.repeat) return` ——
> 顺带修掉了长按 `R` 连续重置、长按 `C` 连续切视角。
> 实测见 `experiments/pause-test.mjs`（15/15 通过）。

**座舱视角的三个要点：**

1. **看不到自机** —— 相机在机体内部时，机头/机翼/座舱罩会糊在画面上挡视线。
   做法是在 `scene3d.js` 里 `aircraft.visible = mode !== "cockpit"`。
   `aircraft` 是顶层组（程序化机体与 GLB 二选一），整组隐藏即可；相机位置**不做插值**，
   刚性跟随机体，否则会有“镜头游泳”和延迟。

2. **地平线必须跟着飞机倾斜** —— 这一条最容易错。相机默认 `up` 是世界 `(0,1,0)`，
   如果座舱里也用它，飞机滚转时**地平线永远是水平的**，人感觉不到自己在侧倾。
   正确做法是让 `up` 跟随机体：

   ```js
   camera.up.set(0, 1, 0).applyQuaternion(aircraft.quaternion);
   ```

3. **仪表板要有「坐在座舱里」的感觉，不是把面板挪到正中悬浮** —— 见 `index.html` 的
   `body.cam-cockpit`：

   - **贴底**：面板锚在底部（`bottom:-1.2vh`），不再 `translate(-50%,-50%)` 居中
   - **向后倾斜**：`perspective(1150px) rotateX(10deg)` + `transform-origin:50% 100%`
     → 顶边后退变窄，形成梯形透视，读起来就是“眼睛下方的仪表板”
   - **眉檐遮光罩**：`::before` 在面板上方横贯整片视野的暗带
   - **表框**：用 `box-shadow` 展开（`0 0 0 5px #0b0f14`…）而不是 `border`——
     不占布局，避开 `box-sizing` 问题
   - **四角螺钉**：`::after` 用四个 `radial-gradient`

   > **坑（重要）**：给面板加 CSS 变换后，`main.js` 的 `fit()` **不能再用**
   > `getBoundingClientRect()`。它返回的是**变换后的投影尺寸**，会让画布
   > backing store 分辨率和传给 `drawPFD` 的 `w/h` 一起算错。
   > 改用 `offsetWidth/offsetHeight`（布局尺寸，不受 transform 影响）。
   >
   > 画布尺寸也随之变了：PFD 从 600×288 变成 `height:31vh; aspect-ratio:.85`，
   > ECAM 变成 `aspect-ratio:1.30`。`experiments/pfd-overlap.mjs` 已同步尺寸表
   > （9 种尺寸零重叠），`experiments/cockpit-panel-check.mjs` 专职覆盖新比例。
   >
   > 注：全量两两字形检测会报出 `"120"×"120"`、`"4500"×"4500"` —— 那是速度/高度带上的
   > **高亮数值框盖住同值刻度标签**，框不透明且后画，属设计性遮挡，不算重叠。

   > 另一个陷阱：`camera.up` 必须在 `camera.lookAt()` **之前**设。
   > `lookAt` 会立即用当时的 `up` 算朝向，设在后面这一帧不生效。
   > 原代码是“先 lookAt 再 set up”，只因恒为 `(0,1,0)` 才一直没暴露。

  实测：坡度 `phi = -6.29°` 时 `camUp = [-0.101, 0.992, 0.079]`，
  与 `sin(-6.29°) = -0.110` 吻合 —— 旧行为在这里会得到 `0`。

**仪表盘居中**：座舱视角下把 `#instPanel` 移到屏幕正中并放大（PFD 上 / ECAM 下竖排），
靠 `body.cam-cockpit` 提升优先级实现，**只有一份 canvas 实例**，不重复绘制。
注意加了 `pointer-events:none`，否则会挡住 3D 视景的点击（见上文 `#trendPanel` 那个坑）。

**已删除的塔台视角**：原来有个固定在地面 700m 外的“塔台机位”，
飞高空时它只能看到一个点，没有信息量；且 `MODES` 里多一个模式就多一份维护成本。

## 真实地理底图（src/scene/geo.js）

已实测**允许跨域**的两个服务（浏览器直接抓取，返 200）：

| 用途 | 服务 | URL 模板 |
|---|---|---|
| 卫星影像 | Esri World Imagery | `.../World_Imagery/MapServer/tile/{z}/{y}/{x}`（注意 y 在前） |
| 地形高程 | AWS Terrain Tiles | `s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png` |

两者都是 Web Mercator（EPSG:3857），共用同一套 `(z,x,y)` 编号。
参数：`GEO_ZOOM=12`、`GEO_GRID=5`（5×5 瓦片 ≈ **38km**），共 25 张影像 + 25 张高程。

- **高程编码**：Terrarium 格式，`elev = R*256 + G + B/256 - 32768`（米）
- **地形网格**：一块 96×96 段的 PlaneGeometry，顶点按高程抬起，UV 贴拼接后的影像大图
- **重载**：飞机飞近底图边缘时自动重拉。余量 40%（约 7.6km），**必须大于 雾距/尺寸**，
  否则重载触发前就已经能看见底图边界了（这是之前“场景小、看得到边”的根因）
- **降级**：瓦片全部失败时自动退回程序化地面，不会白屏

**起始位置**：设在纳帕谷（`ic/lat-geod-deg=38.50`、`ic/long-gc-deg=-122.35`，4500ft）——
内陆丘陵葡萄园，纯陆地地形，带起伏高程，卫星影像上辨识度高。
注意 `reset00.xml` 里的 `<latitude>47.0` **并不生效**，必须显式设 `ic/lat-*` / `ic/long-gc-deg`。

### 已修正的 Bug：左侧副翼 / 襟翼装到了右翼上

舵面循环里写的是 `g.position.set(xc, ...)`，`xc` 恒为正；左侧只靠 `g.scale.x = -1` 镜像。
但 **scale 只翻转几何体自身，不改变 Group 的位置**，所以左副翼被摆到了和右副翼完全相同的位置，
两者完全重叠（襟翼同样的问题）。升降舵因为当初是单独写的、用了 `±xc`，反而是对的。

**修法**：`g.position.set(sign * xc, ...)`。

同时给每个舵面命名，并加了 `scene.debugSurfaces()` 返回各操纵面的实际包围盒，
专门用来复查左右是否装反 / 重叠（这类 bug 程序化检查比肉眼可靠）：

```
aileron-R   x=[ +3.18, +4.83]     aileron-L   x=[ -5.57, -3.92]
flap-R      x=[ +0.88, +3.03]     flap-L      x=[ -3.77, -1.62]
elevator-R  x=[ +0.19, +1.94]     elevator-L  x=[ -2.66, -0.91]
rudder      x=[ -0.40, -0.33]
```

**教训**：这类镜像 bug 靠“看代码”很难发现（`scale.x = -1` 看起来就像已经镜像了），
必须真的去量几何体的实际位置。之前没做这一步，所以漏掉了。

### 已修正的 Bug：左襟翼上偏、右襟翼下偏

修完左右重叠之后，肉眼仍能看出不对称：**右侧两个操纵面清晰可见，左侧只剩外侧那个**。
但这次 `debugSurfaces()` 报告的 x 是完美镜像的（±2.325 / ±4.375），看起来“没问题”。

**关键在 y，不在 x**：`flap-R` 中心 y=0.080，`flap-L` 中心 y=0.163，差了 0.083。
原因是我把副翼的差动逻辑 `sign *` 原样抄给了襟翼：

```js
for (const { g, sign } of surfaces.flap) g.rotation.x = sign * FLAP_DOWN;   // ❌
```

- 副翼**需要**差动：正滚转指令 → 右副翼下偏、左副翼上偏，才能产生滚转力矩
- 襟翼是**增升装置**，左右必须**同向**下偏；用 `sign *` 就变成一侧下一侧上

下偏的襟翼垂在机翼下方、一眼可见；上偏的襟翼翘在机翼上方、和机翼糊在一起——
这就是“右侧两个、左侧只有一个”的来源。

**修法**：`for (const { g } of surfaces.flap) g.rotation.x = FLAP_DOWN;`（去掉 `sign *`）

同时给 `debugSurfaces()` 增加了 `deflY`（后缘相对铰链的垂直偏移，<0 下偏 / >0 上偏）：

| 舵面 | x | deflY | 判定 |
|---|---|---|---|
| flap-R / flap-L | ±2.325 | **-0.0417 / -0.0417** | ✅ 同向下偏 |
| aileron-R / aileron-L | ±4.375 | -0.0024 / +0.0024 | ✅ 差动 |
| elevator-R / elevator-L | ±1.425 | +0.0001 / +0.0001 | ✅ 同向 |

**教训（第二次）**：镜像对称要**同时比 x 和偏转方向**。只比 x 会认为“完全对称”，
而只比偏转方向又会漏掉位置装反。两个维度都要量。

### 已修正的问题：机动时飞机“抽搐”

**症状**：平飞完全平滑，一打杆（上下左右）就抽搐。

**根因**：物理固定步长 + 渲染不做插值。每帧消耗的步数取决于累计时间落在哪里；
帧率不是 120 的整数分频时（自适应刷新率 / 高刷屏 / 掉帧），步数在 1、2 之间跳。

**为什么只在机动时看得见**：量化误差固定是“1 个 DT 步的量”，但**可见度取决于变化速率**：

- 平飞：一步 = 0.34m 位移，在 13.5m 机位距离下看不出来
- 机动：一步 = 0.3° 姿态，1 步还是 2 步的差别**直接变成可见的角度跳动**

**修法**：`main.js` 存 `app.prevSt`，用累计器余量 `alpha = acc/DT` 在“上一步/当前步”之间插值
（航向跨 360→0 走最短路径）。任何帧率下动作都连续。

同时给舵面加了作动器速率限制（3.2 rad/s）：键盘是离散 0/1 输入，`ail` 会一步从 0.054 跳到 -0.89，
不限制的话舵面会“瞬移”。真实舵机本来也有速率上限。

#### 排查中踩的两个坑（值得记下）

1. **后台节流假象**：一次采样看到 0.1fps（每帧 16.8s），以为场景太重建崩了；
   实际是 `visibilityState: hidden` 时浏览器把 rAF 节流了，与性能无关。
2. **采样率混叠（最坑）**：我用 rAF（60Hz）采样，而物理跑 120Hz。
   看到的“3 次符号翻转 ≈ 1.5Hz 振荡”完全是**混叠出来的假信号**——
   真实频率可能是 118.5 或 121.5Hz。
   后来改成逐物理步采样（劫持 `app.st`/`app.out` 的 setter，不动源码）才可靠。

判定证据：前台 60Hz 实测位置跳变恒定 0.673m、姿态 90 帧内变化 < 0.0002°——
**物理本身是平滑的**；而后台那次跳变只有 `0.673 / 1.347 m` 两个取值（精确 1:2），
正是整数步长量化的直接证据。

**教训（第三次）**：**采样率不够会制造假象**。用 60Hz 采样去判断 120Hz 的信号，
得到的“振荡频率”是假的。判断控制回路是否振荡必须逐物理步采样。

**想换成自己的模型**：把 `scene3d.js` 的 `AIRCRAFT_GLB` 指到你的 .glb 即可，
缩放与朝向有自动归一化（包围盒反推机身长度；机头按 `+X` 约定转到 `-Z`）。

## 已验证的实验结论

`node experiments/proof.mjs` — 每个 case 都先由飞控稳定到平飞获得**一致起点**，再只切换法则/注入故障，施加**完全相同**的飞行员输入：

| 实验 | 无飞控（DIRECT） | 有飞控（NORMAL） |
|---|---|---|
| A 松杆不操纵 | 高度漂移 147 ft | 高度漂移 **43 ft** |
| B 满杆拉到底 | 迎角冲到 **44.8°（失速）** | 迎角被摁在 **8.1°** |
| C 迎角传感器故障 | —— | 自动降级 ALTN，迎角峰值 **8.1° → 62.7°** |

> 上表数字对应 `Kbeta = -0.35`（已修正）。修正前每个用例的起始速度只有 86kt，
> 因为稳定平飞阶段一直在用满舵对抗侧滑、白掉了 24kt；修正后回到 96kt。

### 已修正的 Bug：偏航通道符号错误

`src/fcs/fcs.js` 里侧滑抑制项原为 `rud = Kr*r + Kbeta*beta`，`Kbeta = +0.35`。
但按文件顶部的符号约定，**正舵令 = 左偏航**；而 `beta > 0` 表示机头偏在速度矢量左侧，
要消除它必须**右偏航（负舵令）**。所以 `Kbeta` 取正号是**正反馈**：

```
beta↑ → 舵令更正（左） → 机头更偏左 → beta↑↑ … → 方向舵饱和在 +1.0
```

实测症状（浏览器内）：侧滑角稳定在 **14~15°**、方向舵**长期饱和**、
速度从 110kt 被侧滑阻力拖到 **67kt**。改为 `Kbeta = -0.35` 后：
侧滑 **0.03°**、方向舵 ≈ 0、坡度 0.1°、速度收敛到 74kt 新平衡点。

**为什么之前没被发现**：`experiments/proof.mjs` 的三个实验（A/B/C）全部是**纵向**的，
`grep beta experiments/proof.mjs` 零命中——**偏航通道从未被任何测试覆盖**。

实验 C 是最有说服力的一条因果链：**传感器坏了 → 飞控算不出保护 → 自动降级 → 保护真的消失 → 飞机真的会失速**。降级不是界面动画。

### 为什么先做「时间历程」

Kbeta 符号错误（β 14–15°、方向舵饱和、速度掉到 67kt）是靠人眼看飞机「不对劲」才发现的。
`proof.mjs` 全程只做纵向 A/B/C 断言，横航向的 β、方向舵、侧向过载**从未被画出来、也从未被断言**。
录一条 β 曲线，这类错误会在几秒内暴露成一条 14° 的平线。

**它是展示手段，同时是验证手段。**

### 新增文件

- `src/rec/recorder.js` —— 环形缓冲（36000 点 @60Hz ≈ 10 分钟）、`toCSV()`、区间二分查询
- `src/rec/eventlog.js` —— 分级日志；带去重窗口（保护介入是**每步**都在触发的，不去重会瞬间刷满）

## 本次改造踩到的坑

### 1. `#instPanel` 收不起来（CSS 优先级）

`#instPanel .pb{display:flex}` 带 ID，优先级 `(0,1,1,0)`，
**压过**了 `.panel.collapsed .pb{display:none}` 的 `(0,0,3,0)`。

实测症状：点收起后面板看着收了，`#pfd` 宽度**仍是 248px**，画布还在原地继续渲染。
日志面板和条带图面板没有这个 display 覆盖，所以它们正常 —— 只坏了一个面板，很容易漏掉。

→ 修法：`.panel.collapsed .pb{display:none!important}`。

### 2. 媒体查询断点 980px 定得太高

原本 `@media (max-width:980px){ #trendPanel,#logPanel{display:none} }`。
很多笔记本窗口宽度都会掉进去，结果**新增的条带图一进来就被隐藏**。

实测症状：`#trend` 画布停在 HTML 默认的 300×150、非空像素为 0（`fit()` 因尺寸过小提前返回）。

→ 修法：拆成 `max-width:1180px` 让日志先让位、`max-width:900px` 再让条带图让位（条带图优先级高于日志）。

### 3. 事件日志时序

法则变更靠 `fcs.statusLog` 在下一步物理步播报，
导致 `当前法则 DIRECT` 排到了 `法则 NORMAL → DIRECT` **前面**，读起来是反的。

→ 修法：把冲刷抽成 `drainLawEvents()`，预设施加故障后**立即**调用。

### 4. `#trendPanel` 收起后仍占满 152px（真浏览器全宽复测发现）

与第 1 条**同一类**的 ID 选择器优先级问题，但位置不同：

```css
.panel.collapsed{width:auto;height:auto}   /* (0,2,0) */
#trendPanel{bottom:56px;left:8px;right:8px;height:152px}  /* (1,0,0) —— 压赢 */
```

`#logPanel` / `#instPanel` 没在**面板级**写死高度（只写了 `.pb` 子元素），所以它们收起正常。
只有 `#trendPanel` 把高度写在了面板上，于是收起后：

| 面板 | 收起后尺寸 | `elementFromPoint(中心)` |
|---|---|---|
| `#logPanel` | 306 × 31 | `ph`（标题栏）✓ |
| `#instPanel` | 318 × 31 | `ph`（标题栏）✓ |
| `#trendPanel` | 1584 × **152** ✗ | `trendPanel` 自身 ✗ |

**它是 Bug，不是外观问题**：收起后的面板依然盖住 3D 视景底部一条 1584×152 的区域，
且命中测试返回面板自身 —— 用户点那里想拖镜头/选飞机，**点击被面板吃掉了**，却又看不到任何内容。

→ 修法：`#trendPanel.collapsed{height:auto}`，用 (1,1,0) 压回去。修后 1584×32，命中 `ph` ✓。

> **教训**：`display:none` 不代表元素不占位。收起类功能一定要同时查 **尺寸** 和 **命中测试**，
> 光看“内容不见了”会漏掉“透明的阻挡层”。

### 5. PFD 里 `BANK HOLD` 压在航向带上（文字堆积）

顶部原来只用一个拍脑袋的比例分区：

```js
const fmaH = boxH * 0.11;                     // 固定比例
const tapeTop = y0 + fmaH;
const stripY = tapeTop - fmaH * 0.34;         // 航向带又被塞回 fmaH 带内
const fmaY = y0 + boxH * 0.035;               // FMA 也在 fmaH 带内
```

**FMA 与航向带被放进了同一段垂直区间**，而那个 0.11 是拍出来的，根本没算过字高。
用 `experiments/pfd-overlap.mjs` 拦截真实 `fillText` 算字形包围盒，对照量出旧布局：

| 尺寸 | 旧布局与 FMA 第1行重叠 | 与第2行（tags）重叠 |
|---|---|---|
| 座舱 600×288 | 3.4 px | **7.2 px** |
| 原小尺寸 318×196 | 2.3 px | 5.2 px |
| 窄高 300×500 | 3.4 px | **10.1 px** |

第 2 行的 `BANK HOLD · FPA HOLD` 正好压在航向数字上 —— 就是用户在座舱视角看到的现象。
（小尺寸下一直存在，只是座舱视角把 PFD 放大后才显眼。）

→ 修法：把顶部改成**按字体实际高度**自下而上堆三段，而不是拍比例：

```js
const fmaBot = fmaY + fFma * 1.35 + fTag * 0.6;   // FMA 两行下沿
const stripY = fmaBot + fHdg * 1.9 * 0.5;         // 航向带
const tapeTop = fmaBot + fHdg * 1.9 + fHdg * 0.2;// 姿态区
```

注意 `fmaBot` **即使 tags 为空也保留占位**，否则航向带会随模式切换上下跳动。
修后 5 种尺寸全部零重叠，间隙 5.3～9.7 px。

> **教训**：多行文本 + 多条横向带的布局，**不能拍固定比例**。
> 要么按字体量出来的高度算，要么把 “带” 拆成互不相交的独立区间。

### 6. 横滚通道：满杆只能滚到 6°（两个 bug 叠加）

现象：满杆按 A 持续 20 秒，坡度稳定在 **-6.3°** 就不再增加，副翼输出只有 **0.04**。

**Bug A —— `bankRef` 从未被锁存。** `stickNeutral` 只在构造函数里赋值过一次（`:43`），
`update()` 里再没写过，所以 `if (neutralRoll && !this.stickNeutral)` 恒为假，
`bankRef` 永远是 0。对照俯仰通道：它用 `gammaRef === null` 作哨兵，压杆时
`gammaRef = null`，松杆时重新锁存 —— 同一个思路，横滚通道漏了“更新哨兵”这一半。

**Bug B —— 度与弧度混用。** `st.phi` 是**度**（`attitude/phi-deg`），`st.p` 是 **rad/s**。
坡度项 `0.30*(bankRef-phi)*0.5` 直接拿度乘增益（= 0.15 每度），与速率项 `0.85` 每 rad/s
量级接近，于是满杆时两项在 **6°** 就相互抵消：

```
0.85 × 1.05 = 0.8925   ← 滚转指令（pCmd = pMax）
0.15 × 5.95 = 0.8925   ← 坡度“弹簧”（bankRef 恒为 0）
```

`experiments/roll-diag.mjs` 用真实 JSBSim 复现：实测终点 **-6.28°**，解析预测 **-5.95°**，
`bankRef` 全程为 0。四个可观测后果：

| 现象 | 旧 | 修后 |
|---|---|---|
| 满杆 10s 终点坡度 | -6.28°（卡死） | -94.0° |
| 松杆瞬间副翼 | **1.000**（满舵瞬态） | 0.057 |
| 松杆后坡度 | 回 0°（-0.16°） | 保持 -32.8° |
| BANK 保护（>55° 夹到 30°） | 死代码，从不触发 | 生效 |

顺带发现 `bankMax: 55` / `bankReturn: 30` 的保护逻辑写在那个**永不执行的分支里**，
整套横滚保护都是死代码（俯仰通道的同类保护是活的，所以问题只在横滚暴露）。

→ 修法：按俯仰通道的模式重写：`bankRef` 用 `null` 作哨兵；压杆时清空参考、只给纯速率
指令；松杆时锁存坡度；坡度误差按俯仰通道同样的 `/10` 归一化。DIRECT 分支也要
清 `bankRef`，否则从 DIRECT 切回 NORMAL 会用到陈旧的参考。

**仍未解决（比例环固有静差，已量出待决定）**：验收 13/13 通过，但留下两处缺口——
俯仰速率环有 `KiNz` 积分项，而横滚速率环只有 `KpRoll` 比例项：

- 滚转率跟踪只有 **59%**（指令 60°/s，实测 35.5°/s），副翼稳态 0.37 **不饱和**
- 坡度保持静差 **2.4°**（`bankRef=-30.4°` → 稳定 -32.8°）

> **教训**：同一个文件里的“孪生”通道（俯仰/横滚）**已经写出了正确范例**时，改之前先逐行对照。
> 这次哨兵写法俯仰通道是对的，横滚通道照着抄一半就漏了赋值；单位同理——`_deg` 与
> `_rad_sec` 在同一行里混用时，增益就是错的数量级。

### 7. 飞行时卡顿、飞机“前后抽搐”

现象：飞行中规律性卡顿，并且**飞机看起来在屏幕上前后抽动**。

**已排除的两个假设（都写了对照实验，结论是负面结果）：**

1. **相机平滑用了抖动的 dt** —— `camPos.lerp(target, 1 - pow(K, dt))` 看着可疑，
   但它**本身就是帧率无关的幂函数形式**，原始 dt 就是正确输入。
   `experiments/camera-jitter.mjs` 实测：间距抖动仅 **0.16m**（峰峰 0.71m）。
   试过把 dt 夹紧 + EMA 平滑，反而**恶化**到 0.91m（峰峰 3.76m）——
   EMA 让 dt 滞后于真实值，掉帧时追上不足、之后过冲，自己制造振荡。**已回滚。**
2. **`acc = 0` 会让渲染位置后退一步** —— `experiments/acc-reset.mjs` 实测：
   `acc = 0` 与 `acc = min(acc, DT)` 的渲染回退次数**都是 0**。
   因为 guard 打满时循环已推进 60 步，“alpha=0”那个点仍远远领先于
   上一帧的渲染位置。**无需修改。**

**仍未能定位的部分**：上述两个假设都在无头环境里被否定了，
说明症状大概率出在浏览器/GPU 侧（WebGL 帧节奏、地理底图瓦片上传、GC 停顿），
需要在真实浏览器里用 performance 面板才能定位。

**已确认并修复的真实开销：时间历程重绘。** 用确定性指标度量（计时噪声太大，
同一份代码能测出 7ms 和 70ms）：数一次重绘里 `rec.get()` 的调用次数。

```
修复前：约 57,630 次/重绘      修复后：约 36,030 次/重绘   （-37%）
再叠加 15Hz 节流（原 60Hz）：每秒约 3,457,800 → 540,450 次  （-84%）
```

两处修改：

1. **`trend.js` 图例那行重复调了 `rec.range()`。** 原本
   `legend.push({ ..., mn: rec.range(k,i0,i1)[0], mx: rec.range(k,i0,i1)[1] })`
   ——同一个窗口被完整扫了第 2、3 遍（每次都是 `i0..i1` 逐点 `get()`）。
   改成复用上面已经算好的结果（先把未加 padding 的真量程存下来）。
2. **`main.js` 把重绘节流到 15Hz。** 120s 滚动窗，肉眼分不出 60Hz 与 15Hz。

**顺带修的 layout thrashing：** `fit()` 读 `offsetWidth` 会**强制同步布局**，
而渲染循环里紧接着就写 DOM（`lawBadge` / `protoTags` / `clock`），两者交替
就是布局抖动。把 `fit()` 一并移进节流分支，并给每个 DOM 写入加值缓存（写入内容
没变就不碰 DOM —— 即使赋同样的字符串也会让布局失效）。

> **教训**：看到“dt 抖动 → 插值异常”就想去平滑 dt 之前，先确认那个插值公式
> 是不是已经是帧率无关的。`1 - pow(K, dt)` 这类幂函数写法**已经处理了 dt 变化**，
> 再套一层平滑只会引入新的滞后与过冲。**先写对照实验，再改代码。**
> 本轮两个假设都被自己的实验否定了 —— 如果没有做这个验证，就会把两个
> “看起来合理”的错误修改提交进去。

### 8. 舵面独立着色：把【实际偏转】画成颜色

目标：不用看 PFD，光看飞机就知道哪个舵面在动、往哪边动。

**关键：必须按“实际偏转”着色，不能按指令值。**
`setControls` 里有 `slew()` 速率限制（3.2 rad/s），实际舵位与指令值会分叉；
用指令值会出现“显示想让它转多少、实际却没转”的撒谎。所以读的是
`rotation.x`（真实值），配色函数只接这个。

实测（压杆右滚，页面内 rAF 逐帧采样）：

```
指令 0.312 rad  实际仅 0.063 rad    ← 爬升中，颜色跟的是后者
...
指令 0.172 rad  实际 0.172 rad      ← 追上后一致
```

**配色**：青 = 正偏，橙 = 负偏，深石板灰 = 中位。
副翼左右差动 → 两面自然呈现相反颜色，这正是最想看的东西：

```
ailR = +0.177 rad  → #00e5ff（纯青）
ailL = -0.177 rad  → #ff6a00（纯橙）
```

#### 为“教学要显眼”做的三个选择

1. **中性底色用深石板灰 `#39404a`，不是浅灰。**
   最初用 `#d8dde5`（白机体同色），往青/琥珀混色时直接被洗白——
   这就是“颜色太浅”的根因。深色底才能把色阶拉开。
2. **混色走到满饱和**（不乘 0.85），且用青/橙这对最大对比色。
3. **加 `emissive` 自发光。** 追机视角距离 ~13.5m，而且舵面会背光/进阴影；
   自发光不受光照影响，远近都读得出来。中位时 `a≈0` → 不发光。

#### 追机视角可见性：截图 + 像素分类实测

不看数字看画面（`experiments/ctl-visibility.mjs`，裁画面中心 50%）：

| 场景 | 近纯青像素 | 近纯橙像素 |
|---|---|---|
| 中位（对照） | **0** | **0** |
| 压杆右滚 | **599** | **192** |

而且**青跨 x 650–795、橙跨 x 554–592**（画面中心 x=720）——
青在右、橙在左，与“右滚 = 右副翼下偏”完全一致。

> 坑：第一版分类器用“色相区间”，把大片蓝色天空也数了进去（青 2982 像素
> 几乎全是天），舵面变化被淹没。改成**只认接近纯青/纯橙的像素** + 中心裁切才干净。

> ⚠ 老实话：这个距离下舵面只有 **~4px 高**的彩色条，属于“亮色点缀”而不是
> “大片色块”。若还要更明显，只能动追机相机距离、或扩大染色范围（都要改设计）。

#### 实现前必须知道的：材质是共用的

原来**所有舵面共用一个 `ctlMat`**（左右副翼 + 左右升降舵 + 方向舵）。
直接用的话五个面会一起变色，根本看不出差动。必须先拆成
每个舵面一个 `MeshStandardMaterial` 实例。襟翼是静态的，共用一个即可。

#### 两个实测出来的坑

1. **用“行程上限”做分母会让升降舵几乎不变色。**
   正常法则下升降舵峰值只有 **29% 行程**（载荷指令 + 配平洗出），
   线性映射后颜色淡得看不出来（实测只有 25% 混色强度）。
   加了一道显示增益 + 幂次曲线（`CTL_GAIN = 1.8`、指数 `0.8`）。
   > ⚠ 这是纯视觉取舍：**颜色深浅不代表舵面真转到了那个比例**。
   > 真实偏转角请读 `scene.surfaceTint()`，那里是未经修饰的弧度值。

2. **NORMAL 法则下压偏航杆，方向舵几乎不动。**
   因为横滚/俯仰是杆位指令，而方向舵在 NORMAL 下是
   `rud = Kr*r + Kbeta*beta` —— **纯阻尼器，飞行员偏航输入根本没接进去**。
   只有 DIRECT 法则才是 `rud = -stick.yaw` 直连。
   实测：NORMAL 下 rud = 0.051 rad，DIRECT 下 rud = 0.436 rad。
   这反过来成了个很好的教学点：着色让“杆动了舵没动”自己现形。

#### 诊断接口

`scene.surfaceTint()` 返回各舵面的实际偏转角（rad）与当前颜色，
供自动化断言用（不是靠肉眼看）：

```js
{ ailL: { defl, color }, ailR: {...}, elev: {...}, elevL: {...}, rud: {...} }
```

实测见 `experiments/ctl-tint-test.mjs`（18/18 通过，含
“颜色跟的是实际值而非指令值”的逐帧验证）。

## 踩过的坑（重要，改代码前先读）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **发动机启动值** | RPM 恒为 0、推力 0，飞机持续掉速变成"无动力滑翔"，但用户界面看不出异常 | `propulsion/set-running` 必须传 **`-1`**（启动全部）。传 `+1` 会被解释成"启动 1 号发动机"，而 c172 只有索引 0 一个发动机 → 永远不转 |
| **reset 覆盖初始条件** | `reset()` 后用 IC 文件重建状态，之前设的油门/高度全丢 | reset 之后**重新施加** IC 覆盖值（见 `applyIc`） |
| **升降舵符号** | 猜错会导致控制律正反馈发散 | 实测：`elevator-cmd` **正 = 低头**。要抬头/加载荷必须用**负值** |
| **PropertyBatch 不存在** | README 里有 `createPropertyBatch`，但已发布的 `1.2.4-beta.4` 没有该 API（特性是发布之后的提交） | 代码里已带降级回退。14 个属性逐个读约 50µs/步，120Hz 下开销可忽略 |
| **定步长累加器** | `last = now` 写在算 `dtReal` 之前 → `dtReal` 恒为 0 → 物理永远不推进 | 必须先算 `dtReal` 再更新 `last` |
| **核心包很年轻** | `@0x62/jsbsim-wasm` 仅 4 star、作者自述早期开发 | 动力学已隔离在 `adapter.*.js` 后面，换实现不影响上层 |
